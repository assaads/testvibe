# Testvibe — scenario-driven, agent-driven real-usage testing for any tool (+ syncestra reference)

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking. This plan **supersedes** the earlier library-only version of this file. Detailed syncestra RC test code also lives in `2026-07-29-real-usage-testing-behavior-gate.md` (Tasks 6–11) and is reused in Phase D.

**Goal:** Build **`testvibe`** — a deterministic testing engine + an MCP server + an autopilot skill that gets *any* tool integrating with external systems to full real-usage E2E coverage, where a **coding agent** (Claude Code / Codex) is the intelligence (Testvibe ships **no bundled LLM**). Prove it on **syncestra** across all surfaces, **nothing deferred.**

**Architecture — scenarios × surfaces, agent-driven:**
- A tool writes its **real-world scenarios** as ordinary pytest tests tagged `@scenario`. Each scenario exercises the tool's ops on a real (or hermetic) environment and asserts outcomes.
- Testvibe's **pytest plugin** (auto-activated on `pip install testvibe` via the `pytest11` entry point) augments every scenario with the **surface dimensions**: invariant checks (`@invariant`), perf telemetry, advisory signals, and the S7 captured-failure corpus auto-pin. So the 8 surfaces are *checks applied to scenarios*, not a fixed test list.
- The **MCP server** exposes the engine to a coding agent: `run_scenario`, `get_run_report`, `list_coverage_gaps`, `list_advisories`, `add_corpus_entry`, `promote_corpus`. The **agent is the AI** — it reads reports, proposes scenarios, distills repros, and writes test code. Testvibe never calls an LLM.
- The **autopilot skill** (`testvibe-autopilot`) composes the granular tools into one autonomous loop the agent runs. Granular tools stay individually usable.
- `testvibe init` scaffolds the scenario skeleton; `testvibe upgrade` refreshes it while preserving tool-specific code via `# testvibe:keep` regions.

**Tech Stack:** Python ≥3.11, hatchling, pydantic v2, pytest (+ hypothesis for S7 fuzz), FastMCP (MCP server, optional extra), PyYAML, detect-secrets. Reference instantiation: syncestra (Typer/FastMCP/GitPython/PyGithub).

## Global Constraints

- **`testvibe` is a new standalone package/repo** (`github.com/assaads/testvibe`), Python ≥3.11, hatchling build, release-on-push like syncestra.
- **Scenarios are native pytest tests.** A scenario is a `def test_*` function decorated with `@scenario(name, kind=...)`. `kind ∈ {hermetic, canary, dogfood}`: hermetic runs in the gate; canary/dogfood run on schedule. Testvibe never reimplements a test runner — it uses pytest.
- **No bundled LLM.** Testvibe makes zero AI API calls. The coding agent (via the MCP server or the autopilot skill) is the intelligence. `advisory`/`coverage_gaps` produce *data*; the agent interprets it. An **optional** `TESTVIBE_LLM_*` path exists ONLY for a headless scheduled autopilot (Phase D provisioning); the primary mode is agent-driven.
- **AI proposes, deterministic disposes.** Pinning/promotion always goes through deterministic checks (`xfail(strict)`). The autopilot may autonomously write/fix **test** code and seed the corpus; changes to the **tool's own source** require a human review gate.
- **`# testvibe:keep` regions are sacred.** `testvibe upgrade` regenerates scaffolding but never overwrites a keep-region. This is what makes the generator safely re-runnable.
- **Secrets via vault/CI secrets only.** The canary PAT is a CI secret (`SYNCESTRA_CANARY_PAT`); `testvibe.report` redacts all captured output via `detect-secrets` before any report is written/alerted.
- **syncestra RC2/RC4/RC5 fixes are already on `main`** (`aa9a12d`) — Phase D proves Testvibe catches/pins them.
- Conventional Commits.

```python
# src/testvibe/scenario.py
from __future__ import annotations
from typing import Callable
SCENARIOS: dict[str, dict] = {}
INVARIANTS: dict[str, Callable] = {}

def scenario(name: str, *, kind: str = "hermetic", surfaces=("invariant", "perf", "advisory")):
    """Tag a pytest test as a testvibe scenario. kind=hermetic|canary|dogfood."""
    import pytest
    def deco(fn: Callable) -> Callable:
        fn = pytest.mark.testvibe_scenario(fn)
        fn.__testvibe__ = {"name": name, "kind": kind, "surfaces": tuple(surfaces)}
        SCENARIOS[name] = {"fn": fn, "kind": kind, "surfaces": tuple(surfaces)}
        if kind != "hermetic":
            fn = pytest.mark.skip(reason=f"{kind} scenario; run via scheduler/MCP")(fn)
        return fn
    return deco

def invariant(name: str):
    """Register an invariant check (asserted alongside scenarios by the plugin)."""
    def deco(fn: Callable) -> Callable:
        INVARIANTS[name] = fn
        fn.__testvibe_invariant__ = name
        return fn
    return deco
```
```python

# src/testvibe/corpus.py
from __future__ import annotations
import importlib.util
from pathlib import Path
import yaml
from dataclasses import dataclass

@dataclass
class CorpusEntry:
    id: str; invariant: str; discovered_at: str; source: str; repro: str; status: str

def load_corpus(path) -> list[CorpusEntry]:
    p = Path(path)
    if not p.exists(): return []
    return [CorpusEntry(**e) for e in (yaml.safe_load(p.read_text()) or [])
            if e.get("status") in ("open", "pinned")]

def _load_repro(repro_path):
    rp = Path(repro_path)
    spec = importlib.util.spec_from_file_location(rp.stem, rp)
    mod = importlib.util.module_from_spec(spec); assert spec.loader
    spec.loader.exec_module(mod); return mod.repro

def quarantine_tests_for(entries):
    return [(f"test_quarantine__{e.id.replace('-', '_')}", _load_repro(e.repro), e.status) for e in entries]
```

```markdown
# testvibe autopilot

You are the AI intelligence layer for testvibe (testvibe itself is deterministic
and makes NO LLM calls — YOU are the AI). Run the full loop using the testvibe
MCP tools + your own read/write/run tools.

## Loop
1. **Discover** the target tool: Read its README/contract, Grep its ops, inspect
   any real-usage traces. Build a mental model of its external boundaries and
   invariants.
2. **Draft scenarios**: from the tool's behavior + traces + coverage gaps (call
   `list_coverage_gaps`), write `@scenario` tests for the real-world shapes not
   yet covered, into the tool's `tests/testvibe/`.
```
